Microservice BankApplication Architecture Notes

Microservices Architecture?

	Microservices Architecture is an architectural style in which a large application 
	is divided into a collection of small, independent services.

	Each service is responsible for a specific business capability, 
	runs in its own process, can be developed, deployed, and scaled independently, 
	and communicates with other services using lightweight protocols such as REST, gRPC, or messaging (Kafka/RabbitMQ). 

	This architecture promotes loose coupling between services and high cohesion within each service.

	Microservices Architecture is an architectural style that decomposes a 
	large monolithic application into a collection of small, loosely coupled, 
	highly cohesive, independently deployable services.



Adv MS?	:)
	=> Smaller code base is easy to maintain.
	=> Easy to scale as individual component.
	=> Technology diversity i.e. we can mix libraries, databases, frameworks etc.
	=> Fault isolation i.e. a process failure should not bring whole system down.
	=> Better support for smaller and parallel team.
	=> Independent deployment
	=> Deployment time reduce

Microservices Challenges	:(

	=> Difficult to achieve strong consistency across services
	=> ACID transactions do not span multiple processes.
	=> Distributed System so hard to debug and trace the issues
	=> Greater need for end to end testing
	=> Required cultural changes in across teams like Dev and Ops

lease-renewal-interval-in-seconds: 
		Client sends heartbeat to Eureka every 30 seconds to say “I am alive.”
		
lease-expiration-duration-in-seconds: 
		If no heartbeat is received within 90 seconds, Eureka removes the instance (marks it dead).


Note:
 Eureka Self-Preservation Mode
		What it is: A safety mechanism where Eureka stops removing instances even if heartbeats are missing
		(to avoid mass failure during network issues).
		
		Why it exists: During network glitches, many services may look “down” falsely → without this, 
		Eureka would wipe them all out.
		
		⚙️ Key Point
		When enabled → Eureka trusts services are alive (better safe than sorry)
		When disabled → Eureka aggressively removes instances (good for testing, risky in prod)

🔧 Config
	eureka:
	  server:
		enable-self-preservation:

step 7.Configure resilence 4j to Bank application

Resilance 4j
--------------
What is Resilience4j?
---------------------
A library to make your service fault-tolerant
	It prevents:
	Cascading failures
	Thread exhaustion
	System crashes

Solution Order (VERY IMPORTANT)
-------------------------------
RateLimiter → Bulkhead → TimeLimiter → CircuitBreaker → Retry


We can apply Resilience4j to indidual microservice to achive different patterns
----------------------------------------------------------------------
RateLimiter  -> How many requests per second?

Bulkhead     -> How many concurrent requests?

TimeLimiter  -> How long should we wait?

CircuitBreaker -> When should we stop calling?

Retry        -> When should we try again?


Recommended Order
-------------------
Client Request
      │
      ▼
RateLimiter      (protect from traffic spikes)
      │
      ▼
Bulkhead         (limit concurrent resource usage)
      │
      ▼
TimeLimiter      (avoid waiting forever)
      │
      ▼
CircuitBreaker   (stop calling unhealthy services)
      │
      ▼
    Retry            (recover from transient failures)
      │
      ▼
Remote Servic

First control traffic → then handle failure
--------------------------------------
	  Client
		↓
	RateLimiter
		↓
	CircuitBreaker
		↓
	  Retry
		↓
	Service Call (Feign / RestClient)


This starter gives you:
----------------------
<dependency>

  <artifactId>spring-cloud-starter-circuitbreaker-resilience4j</artifactId>

		Auto integration with:
		OpenFeign
		RestClient / RestTemplate
		LoadBalancer

	“Spring-managed Resilience4j (clean + production-ready)”

Bulkhead Patterns
-------------------
Bulkhead is a resilience pattern that isolates resources by 
limiting concurrent access to a dependency, preventing one slow or 
failing service from exhausting the application's resources.


Problem: A slow service can block all application threads.

Solution: Bulkhead allows only a limited number of concurrent 
			calls to that service, protecting the rest of the application.


 
Order Service Example
      |
      +--> Account Service (Fast)
      |
      +--> Card Service (Slow)

Without Bulkhead:
Slow Card Service can occupy many threads and affect the entire application.

With Bulkhead:
Only a fixed number of requests can call Card Service.
Other requests continue to work normally.

Without Bulkhead
-----------------
Tomcat (200)---> 200 requests---> Card Service---> All waiting

With Bulkhead
Tomcat (200)---> Bulkhead---> Only 5 requests allowed----> Card Service

IMPORTANT Questions
-----------------------
What is the default Bulkhead implementation in Resilience4j?

Semaphore Bulkhead. It uses a semaphore to limit the number of concurrent executions. 
It does not create a separate thread pool.


When is a ThreadPoolBulkhead used?
When you want requests to execute in a dedicated thread pool instead of the caller's thread. 
This is a different implementation from the default Semaphore Bulkhead.


Bulkhead controls how many concurrent calls are allowed.
TimeLimiter controls how long a call is allowed to wait.

step 6: resourceserver will fetch certificates from auth server
-------------------------------------------------------
When the Resource Server receives a JWT token from the client,
 it does not know whether the token is genuine or fake.

 So, using the jwk-set-uri configuration, it connects to Keycloak's certs endpoint and downloads its public keys (certificates).
 It then uses these public keys to verify the digital signature of the JWT token. 
 
 If the signature is valid, it means the token was really issued by Keycloak and has not been tampered with, so the request is allowed. 
 If the signature verification fails, the Resource Server rejects the request with 401 Unauthorized.
 
 

		
		
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          jwk-set-uri: "http://localhost:7080/realms/master/protocol/openid-connect/certs"

public class KeycloakRoleConverter  implements Converter<Jwt, Collection<GrantedAuthority>> {
    @Override
    public Collection<GrantedAuthority> convert(Jwt source) {
        Map<String, Object> realmAccess = (Map<String, Object>) source.getClaims().get("realm_access");
        if (realmAccess == null || realmAccess.isEmpty()) {
            return new ArrayList<>();
        }
        Collection<GrantedAuthority> returnValue = ((List<String>) realmAccess.get("roles"))
                .stream().map(roleName -> "ROLE_" + roleName)
                .map(SimpleGrantedAuthority::new)
                .collect(Collectors.toList());
        return returnValue;
    }
}

@Configuration
@EnableWebFluxSecurity
public class SecurityConfig {
    @Bean
    public SecurityWebFilterChain springSecurityFilterChain(ServerHttpSecurity serverHttpSecurity) {
        serverHttpSecurity.authorizeExchange(exchanges -> exchanges.pathMatchers(HttpMethod.POST).authenticated()
                .pathMatchers("/busycoder/accounts/**").hasRole("ACCOUNTS")
                .pathMatchers("/busycoder/cards/**").hasRole("CARDS")
                .pathMatchers("/busycoder/loans/**").hasRole("LOANS"))
                .oauth2ResourceServer(oAuth2ResourceServerSpec -> oAuth2ResourceServerSpec.jwt(jwtSpec ->
                        jwtSpec.jwtAuthenticationConverter(grantedAuthoritiesExtractor())));
        serverHttpSecurity.csrf(csrfSpec -> csrfSpec.disable());
        return serverHttpSecurity.build();
    }

    private Converter<Jwt, Mono<AbstractAuthenticationToken>> grantedAuthoritiesExtractor() {
        JwtAuthenticationConverter jwtAuthenticationConverter =
                new JwtAuthenticationConverter();
        jwtAuthenticationConverter.setJwtGrantedAuthoritiesConverter
                (new KeycloakRoleConverter());
        return new ReactiveJwtAuthenticationConverterAdapter(jwtAuthenticationConverter);
    }

}
