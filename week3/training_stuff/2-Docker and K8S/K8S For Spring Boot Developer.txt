what is typically included in cloud-native applications
------------------------------------------------------
Cloud-native applications are designed specifically 
to run in cloud environments by leveraging cloud computing principles and infrastructure. 
Here’s a breakdown of what is typically included in cloud-native applications:

Core Components of Cloud-Native Applications
------------------------------------------------------

Microservices Architecture
	Application is broken into small, independent services.
	Each service is responsible for a single business capability 
	and can be deployed independently.

Containers
	Services are packaged in containers (e.g., Docker) 
	to ensure consistent environments across development, testing, and production.

Container Orchestration
	Tools like Kubernetes or OpenShift manage deployment, 
	scaling, and resilience of containerized applications.

DevOps and CI/CD Pipelines
	Continuous Integration and Continuous Delivery/Deployment 
	ensure faster and reliable release cycles.

	Tools: Jenkins, GitHub Actions, GitLab CI, ArgoCD, Tekton.

API-First Design
	Services communicate over lightweight APIs (REST, gRPC, GraphQL).
	Promotes loose coupling and easier integration.

Infrastructure as Code (IaC)
	Use of code to manage and provision infrastructure 
	(e.g., Terraform, AWS CloudFormation).

Cloud-Native Storage & Databases
	Use of scalable and resilient storage solutions:

	Block/Object storage (e.g., S3, Azure Blob)
	NoSQL (e.g., MongoDB, DynamoDB)
	Cloud-managed SQL (e.g., RDS, Cloud SQL)

Service Mesh
	Handles service-to-service communication, security, 
	and observability (e.g., Istio, Linkerd).

Auto-Scaling & Self-Healing
	Applications automatically scale based on load.
	Failed containers/services are automatically restarted.

Observability and Monitoring
	Centralized logging (ELK stack, Fluentd)
	Metrics and monitoring (Prometheus, Grafana, Datadog)
	Tracing (Jaeger, Zipkin)

Cloud Provider Integration
	Managed Services: Databases, message queues 
	(e.g., SQS, Pub/Sub), storage, serverless functions.

	Security & Identity: IAM, VPC, encryption, secrets management.

	Serverless Computing (Optional Part): AWS Lambda,
	 Google Cloud Functions, Azure Functions.

components of k8s:
		Master node / control plan
		-----------------------------
		API server: 
			* Most important component, user intract with api server using imparative/decleartive commands
			* The API server is a component of the Kubernetes control plane that exposes the Kubernetes API. 
			* The API server is the front end for the Kubernetes control plane.
		etcd:
			* Consistent and highly-available key value store used as Kubernetes' 
				backing store for all cluster data.
		kube-scheduler:
			* Workload scheduler
			* Control plane component that watches for newly created Pods with no assigned node, 
				and selects a node for them to run on.
				
		kube-controller-manager: 
			* A process that continously monitor workload/nodes etc
			* desired state vs current state kubernetes
			
		Worker Node:
		-----------
			kubelet:
			* An agent that runs on each node in the cluster. 
			It makes sure that containers are running in a Pod.
			* It create and manage container inside a pod

			* The kubelet takes a set of PodSpecs that are provided through various mechanisms 
			and ensures that the containers described in those PodSpecs are running and healthy.
			 The kubelet doesn't manage containers which were not created by Kubernetes.

			kube-proxy:
			*kube-proxy is a network proxy that runs on each node in your cluster, 
			implementing part of the Kubernetes Service concept.

			* kube-proxy maintains network rules on nodes
			* handle conmmunication among the nodes within the cluster
			
			*These network rules allow network communication to your Pods from network sessions 
			inside or outside of your cluster.

			Container runtime:
			*A fundamental component that empowers Kubernetes to run containers effectively. 
			It is responsible for managing the execution and lifecycle of containers within the Kubernetes 				
			environment.

			Kubernetes supports container runtimes such as containerd, CRI-O,
			 and any other implementation of the Kubernetes CRI (Container Runtime Interface).

Note: default strategies : RollingUpdate
-----------------------------------------
Kubernetes automatically used RollingUpdate.

Default Strategy Configuration
------------------------
If you don’t define anything, Kubernetes internally assumes this:

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 25%
    maxSurge: 25%
	
What These Values Mean
-------------------------
maxSurge: 25%
Kubernetes can create extra pods above the desired replicas during an update.
	Your deployment:
	replicas: 3
	25% of 3 ≈ 1 pod

	So Kubernetes can temporarily run:
	3 desired + 1 extra = 4 pods
	
maxUnavailable: 25%
	Maximum number of pods that can be unavailable during the update.
	25% of 3 ≈ 1 pod
	So at least 2 pods must remain available.
	
	

RollingUpdate Strategy
----------------------
maxSurge
--------
maxSurge: 1
--------------
Meaning → Kubernetes can create 1 extra pod during rollout.

 spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
  
   Switching from v1 to v2 	
   kubectl rollout history deploy

----------------
Meaning → Kubernetes can create up to 100% extra pods.

Recreate strategy
-----------------
Recreate strategy, Kubernetes does a very simple but brutal thing:
	Kill all old pods first → then start the new pods.
	No gradual replacement. No overlap. Just a full stop and restart.

Why Recreate Exists
	Even though it causes downtime, it’s useful when two versions cannot run together.
	Database schema changes
	Shared file locks / singleton services
	Legacy stateful systems

Kubernetes Service
-------------------
Pods are not stable network endpoints.
	Problems with Pods:
		Pod IP changes when Pod restarts
		Pods are created and deleted frequently
		Client cannot track Pod IPs
		
		So Kubernetes introduces Service.
		A Service provides a stable network endpoint 
		that forwards traffic to Pods.
		
		Think of it as a load balancer in front of Pods.
		
Types of Services
------------------
ClusterIP (default)
	Used for internal communication inside cluster.
	Not accessible from outside cluster.
	Pods call service using DNS:
		http://productapp-service:8090
		
		
NodePort
	Exposes application outside cluster.
	Kubernetes opens a port on the node.
		Example:
		NodePort: 30001
		Access:
		http://localhost:30001
		http://productapp-service:8090

LoadBalancer
	Used in cloud environments (AWS, Azure, GCP).
	Creates an external load balancer

Blue-Green Deployment 
--------------------------
Definition
	Blue-Green deployment is a release strategy where two identical
	environments run at the same time:

BLUE  → current production version
GREEN → new version

Traffic is switched from Blue → Green after validation.

Core Idea
--------------
In Kubernetes this is implemented using:

	two Deployments
	+
	different labels
	+
	Service selector switch

	Example labels:

	app=productapp
	version=blue
	version=green

Service routes traffic to pods matching the selector.
-------------------------------------------
Traffic Flow

Initial State
------------
Client
  |
  v
Service
  |
  v
BLUE pods (v1)

After Deploying Green
-------------------
Client
  |
  v
Service
  |
  v
BLUE pods (v1)

GREEN pods (v2)  ← running but not receiving traffic

After Traffic Switch
---------------------
Client
  |
  v
Service
  |
  v
GREEN pods (v2)

Switch happens instantly by updating the Service selector.

Kubernetes Implementation
------------------------
Blue Deployment
	labels:
	  app: productapp
	  version: blue

Green Deployment
	labels:
	  app: productapp
	  version: green

Service decides which version receives traffic.
------------------------------------------------
selector:
  app: productapp
  version: blue

Switch to Green:
version: green

Advantages
------------
	Zero downtime
	Users experience no interruption.
	Instant rollback 
	Switch Service back to Blue.
	Safe production testing

Limitation
--------------
	Both environments run simultaneously, 
	so double resources are temporarily required.

k8s probes:
----------------
Kubernetes Probes 
--------------------
When a container starts, Kubernetes assumes it is healthy unless probes say otherwise.
	Without probes:
		Container started → Pod considered Ready
		That can be dangerous because the application might still be starting.

Probes allow Kubernetes to verify:
-------------------------------------
	Is the container alive?  → Liveness Probe
	Is the container ready?  → Readiness Probe
	Is the container fully started? → Startup Probe

The logical execution order of Kubernetes probes is simple.
------------------------------------------------------
Startup → Readiness → Liveness

Startup Probe: Has the application finished starting?

Readiness Probe: Can this pod receive traffic?

Liveness Probe: Is the application still alive
				Is the application running correctly, or is it stuck/broken?

				Kubernetes periodically asks the container this question.


1️. Readiness Probe
----------------
Purpose:
	etermine whether the pod can receive traffic.

If readiness fails:
	Service → stops sending traffic to that pod
	Pod is still running.

Typical use:
	Application still loading
	Database connection not ready
	Cache warming

Example:
----------
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8090
  initialDelaySeconds: 10
  periodSeconds: 10


Liveness Probe
-------------------
Purpose:
	Detect dead or stuck applications.

If liveness fails:
	Kubernetes restarts the container

Typical cases:
	Deadlock
	Memory corruption
	Application freeze

Example:
------------
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8090
  initialDelaySeconds: 30
  periodSeconds: 15
  
Meaning:
----------
	Check every 15s
	Restart container if unhealthy


Startup Probe 
--------------------
Purpose:
	Used for slow-starting applications.

Without startup probe:
	Liveness probe may kill container too early
	Startup probe disables liveness/readiness until startup completes.

Example
--------
startupProbe:
  tcpSocket:
    port: 27017
  periodSeconds: 1
  failureThreshold: 5

Meaning:

Try for 5 seconds
If Mongo not ready → restart



Probe Types
----------------
Kubernetes supports three probe mechanisms.

HTTP probe
-------------
httpGet:
  path: /health
  port: 8080

Most common for Spring Boot.

TCP probe
--------------
tcpSocket:
  port: 27017

Checks if port is open.

Used for databases.

Exec probe
-------------
exec:
  command:
  - cat
  - /tmp/healthy

Runs command inside container.

Use when HTTP endpoint does not exist.

Persistent Volume (PV) and Persistent Volume Claim (PVC) in Kubernetes
------------------------------------------------------------------

What’s the Problem?
	When a container restarts in Kubernetes, 
	any files saved inside it are lost — like saving notes on a whiteboard
	that gets erased when the power goes out.

But you sometimes want permanent storage:
-------------------------------------
	Databases (MySQL, MongoDB)
	Uploaded files
	Logs

Kubernetes Solution: PV + PVC
--------------------------------

1. Persistent Volume (PV) = A physical storage space

	Think of it like a hard disk that lives outside the container.
	Can be local disk, NFS, AWS EBS, GCP Persistent Disk, etc.
	Created by admin or dynamically

2. Persistent Volume Claim (PVC) = A request for storage

	Like saying: “I need a 5GB disk that’s read-write.”
	Created by the developer or app
	Automatically gets matched with a suitable PV

Analogy:
-------------
Real Life												Kubernetes
Parking Lot (empty space)								PV (Persistent Volume)
You rent a spot											PVC (you claim it)
Your car (app) parks there								Pod uses the volume

How It Works Together
-----------------------
	Admin or cloud provider creates a PV
	Your app creates a PVC
	Kubernetes matches PVC to PV
	PVC is mounted to your Pod, and you get permanent storage

Resource Management & Auto Scaling
-----------------------------------
how we can get cpu memory usages of pods?

Resource Management
-------------------
	Kubernetes allows you to control how much CPU and memory each pod can use:

	Requests – Minimum guaranteed resources.
	→ e.g., cpu: 100m, memory: 128Mi

	Limits – Maximum resources a pod can use.
	→ Prevents a pod from consuming too much.

	Helps with fair sharing, performance, and scheduling across the cluster.

Auto Scaling in K8s
--------------------
	Kubernetes can automatically adjust the number 
	of pods or resources based on load.

	Horizontal Pod Autoscaler (HPA)
		Scales pods in/out based on CPU usage or custom metrics.
		e.g., increase replicas when CPU > 80%

	Vertical Pod Autoscaler (VPA)
		Automatically adjusts CPU/memory requests/limits for a pod.

	Cluster Autoscaler
		Adds/removes nodes in the cluster based on pod demands
		(in cloud environments like AWS, GCP, Azure).

How It All Works Together:
-------------------------
	Requests/limits help schedule pods efficiently.
	HPA/VPA adjust pods/resources based on real-time usage.
	Cluster Autoscaler ensures enough infrastructure is available.

-----------------------------------------------
kubectl delete all --all
kubectl get all


2. Apply deployment + service YAML
----------------------------------
kubectl apply -f dep.yaml

kubectl get pods
kubectl get svc

Port-forward:
kubectl port-forward service/productapp 8090:8090

Open browser:
http://localhost:8090/actuator/prometheus

Expected:
You should see lots of metrics text, for example:
jvm_memory_used_bytes
http_server_requests_seconds

This proves Spring Boot metrics are exposed.
Stop port-forward (Ctrl+C).

 Install Prometheus + Grafana
-----------------------------------
Add Helm repo:

helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

Install monitoring stack:
helm install monitoring prometheus-community/kube-prometheus-stack

Expected:

NAME: monitoring
STATUS: deployed

6 Wait for Monitoring Pods
---------------------------
Check pods:

kubectl get pods

Expected pods:

monitoring-grafana-xxxxx
monitoring-prometheus-xxxxx
monitoring-kube-state-metrics

All should be Running.

7 Get Grafana Password (Windows command)
-----------------------------------
Run:

kubectl get secret monitoring-grafana -o jsonpath="{.data.admin-password}" | % { [System.Text.Encoding]::UTF8.GetString([System.Convert]::FromBase64String($_)) }

Expected output:

Abc123xyz

That is the Grafana password.

8 Access Grafana
------------------
Run:

kubectl port-forward deployment/monitoring-grafana 3000:3000

Open browser:

http://localhost:3000

Login:

username: admin
password: <password from step 7>
9 Create ServiceMonitor

Create file:

productapp-monitor.yaml
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: productapp-monitor
  labels:
    release: monitoring
spec:
  selector:
    matchLabels:
      app: productapp
  endpoints:
  - port: http
    path: /actuator/prometheus
    interval: 15s

Apply it:

kubectl apply -f productapp-monitor.yaml

Expected:

servicemonitor.monitoring.coreos.com/productapp-monitor created
10 Verify Prometheus Discovery

Port-forward Prometheus:

kubectl port-forward svc/monitoring-kube-prometheus-prometheus 9090

Open:

http://localhost:9090

Go to:

Status → Targets

Expected:

productapp-monitor   UP
11 Test Prometheus Query

In Prometheus UI run:

jvm_memory_used_bytes

Expected:

graph with JVM metrics

If data appears → scraping works.

12 Import Grafana Dashboard

In Grafana:

Dashboards → Import

Use dashboard ID:

4701

This is Micrometer JVM dashboard.

Expected graphs:

JVM Heap Memory
HTTP Requests
CPU Usage
Threads
GC Activity
Final Architecture
Spring Boot App
      │
      ▼
Service
      │
      ▼

      │
      ▼

      │
      ▼
Grafana Dashboard
What You Achieved

You now have:

Spring Boot metrics
Prometheus scraping
Grafana dashboards
Kubernetes monitoring

This is real production-style observability architecture.
