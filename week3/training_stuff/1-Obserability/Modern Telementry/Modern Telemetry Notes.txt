What Does OpenTelemetry Standardize?
-------------------------------------
OpenTelemetry provides a common standard for collecting and exporting:

Logs – Application and system events.
Metrics – Numeric measurements such as CPU usage, memory, request count, and latency.
Traces – End-to-end request flow across distributed services.

Instead of each vendor using its own protocol, OpenTelemetry uses a single standard:

OTLP (OpenTelemetry Protocol)
---------------------------
Why OTLP Matters

OTLP is to observability what JDBC is to databases or HTTP is to web communication.

	Application
	    ↓
	OpenTelemetry SDK
    	↓
	OTLP
	  ↓
	Collector
	↓
	Grafana
	Jaeger
	Datadog
	New Relic
	Splunk
	Azure Monitor

The application does not need to know which backend is receiving the telemetry.

Benefits of OpenTelemetry
--------------------------
	Vendor-neutral
	Open standard (CNCF)
	Single instrumentation API
	Unified telemetry format
	Supports logs, metrics, and traces
	Easy backend migration without changing application code

Key Takeaway
------------
OpenTelemetry is not a monitoring tool or a storage system.
 It is an open standard that defines how telemetry is collected, represented, and transmitted. 
 The critical innovation is OTLP (OpenTelemetry Protocol),
 which enables applications to send logs, metrics,
 and traces to any compatible observability backend using a single, 
 vendor-neutral protocol. This aligns with the README you shared, which emphasizes that the protocol
 (OTLP) is what matters, not the specific library or backend.

Trace ID
-----------
A Trace ID uniquely identifies an entire request as it travels across multiple services.

Example
GET /accounts/10
Trace ID = 123ABC

The same Trace ID is propagated to every service handling the request.

Browser -> API Gateway -> Account Service -> Loan Service -> Card Service
                  (Trace ID = 123ABC shared across all services)
				  
				  
Key Points
--------------
One request = One Trace ID
Shared across all microservices
Used to search the complete request journey
Enables end-to-end request correlation


Span
----------
A Span represents a single unit of work performed during a request.

Example
Controller -> Service -> Repository -> Database -> REST API -> Kafka

Each operation creates its own Span.

Key Points
-------------
One operation = One Span
Every Span has a unique Span ID
Measures start time, end time, duration and metadata
Parent-child relationships form the execution hierarchy


Trace
--------
A Trace is the complete execution path of a request and consists of one or more related spans.

Trace = Controller Span -> Service Span -> Database Span -> REST API Span -> Kafka Span

Or
Trace = Span 1 + Span 2 + Span 3 + Span 4 + Span 5

Relationship
-------------
1 Request -> 1 Trace -> Multiple Spans


Quick Comparison
------------------------------------------------
Trace								Span
------------------------------------------------
Complete request journey		Single operation within a request
One Trace ID					One Span ID
Shared across all services		Unique for every operation
Contains multiple spans			Belongs to one trace

Easy Analogy 
-----------------
Train Journey = Trace
Each Railway Station = Span



One customer request = One Trace
Each method/API/DB call = One Span
Trace = Collection of Spans

@RestController
public class HomeController {

    private static final Logger log = LoggerFactory.getLogger(HomeController.class);

    @GetMapping("/")
    public String home() {
        log.info("Home endpoint called");
        return "Hello World!";
    }

    @GetMapping("/greet/{name}")
    public String greet(@PathVariable String name) {
        log.info("Greeting user: {}", name);
        simulateWork();
        return "Hello, " + name + "!";
    }

    @GetMapping("/slow")
    public String slow() throws InterruptedException {
        log.info("Starting slow operation");
        Thread.sleep(500);
        log.info("Slow operation completed");
        return "Done!";
    }

    private void simulateWork() {
        try {
            Thread.sleep(50);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

Custom Observation (@Observed / ObservationRegistry
-------------------------------------------------

Why do we need custom observations?
--------------------------------------
Spring Boot automatically creates observations for:
HTTP Requests
JDBC Calls
RestClient/WebClient Calls

Example:
Browser -> Controller

This generates an HTTP span automatically.

What's the problem?
-------------------------
Spring Boot does not know your business logic.

For example:
-----------------
Payment Processing
Fund Transfer
Loan Approval
Interest Calculation
Salary Processing

These are business operations, not framework operations.
So no separate business span is created automatically.

Solution
-------------
Create custom observations for important business methods.

Two options are available:
----------------------------
Option 1 (Recommended)
@Observed: Creates observations automatically using Spring AOP.

Option 2
ObservationRegistry: Creates observations programmatically using Java code.

Without @Observed
-----------------
Browser -> Controller -> Service -> Repository
One HTTP Span

You only see the overall request.

With @Observed
-------------------
Browser -> Controller -> Service(@Observed) -> Repository

HTTP Span
      |
Business Span

Now you can measure only the business operation.

When should we use @Observed?

Use it for important business operations such as:
--------------------------------------------
Payment Processing
Fund Transfer
Order Placement
Report Generation
Inventory Update
Loan Approval

Benefits
-------------
 Creates custom business spans
 Measures execution time
 Adds custom tags
 Visible in Grafana Tempo
 Uses Spring AOP (No boilerplate code)

@Observed vs ObservationRegistry
------------------------
@Observed → Annotation-based, easiest approach.
ObservationRegistry → Programmatic API for advanced/custom scenarios.


Spring Boot automatically observes framework operations (HTTP, JDBC, RestClient), but 
it cannot identify business operations.
 
We use @Observed or ObservationRegistry to create custom observations for business logic, 
enabling separate spans, metrics, and execution timing for important application workflows.

Option 1 : @Observed (Recommended)


What is @Observed?
@Observed is a Micrometer annotation that automatically
 creates a Business Observation around a method.

@Service
public class GreetingService {
    @Observed(name = "greeting.service",contextualName = "Generate Greeting")
    public String greet(String name) {
        try {
            Thread.sleep(100);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }

        return "Hello " + name;
    }
}

Controller
-------------
@RestController
@RequiredArgsConstructor
public class HomeController {

    private final GreetingService service;

    @GetMapping("/greet/{name}")
    public String greet(@PathVariable String name) {
        return service.greet(name);
    }
}

Without @Observed
----------------------
Browser --> Controller --> Service --> Repository
Only HTTP Request Span

With @Observed
-------------------
Browser --> Controller --> GreetingService(@Observed) --> Repository

HTTP Request Span --> Business Span (greeting.service)

Tempo
--------
HTTP GET /greet/Raj --> greeting.service

Internal Flow of @Observed
@Observed --> Spring AOP Proxy --> ObservationAspect --> ObservationRegistry -->
		OpenTelemetry SDK --> OTLP Exporter --> OpenTelemetry Collector --> Tempo --> Grafana

Spring AOP automatically creates and closes the Observation.

Option 2 : ObservationRegistry
-------------------------------
What is ObservationRegistry?

ObservationRegistry is the central Micrometer component responsible for creating and managing Observations.

@Service
@RequiredArgsConstructor
public class GreetingService {

    private final ObservationRegistry registry;

    public String greet(String name) {

        return Observation
                .createNotStarted("greeting.service", registry)
                .observe(() -> {
                    try {
                        Thread.sleep(100);
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    }

                    return "Hello " + name;
                });

    }
}
Internal Flow
--------------------
Business Method --> Observation --> ObservationRegistry --> OpenTelemetry SDK --> OTLP --> Collector --> Tempo --> Grafana



Overall Architecture
---------------------

Why do we need @Observed?
Spring Boot automatically instruments framework components (HTTP, JDBC, RestClient), 
but it cannot identify business operations. @Observed creates separate business spans with minimal code.

What is ObservationRegistry?
The central Micrometer component responsible for creating, managing,
 and recording Observations that are converted into Metrics and Traces.

How does @Observed work internally?
--------------------------
